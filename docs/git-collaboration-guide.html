Team Git Collaboration Guide

Project documentation · reproduced from the private project repository项目文档 · 转载自私有项目仓库

English translation of the original Chinese document.

This document compiles frequently asked questions (Q&A) about project code management, local debugging, and GitHub cloud synchronization, and establishes an initial set of team code management guidelines, aiming to help team members collaborate in multi-person development safely and efficiently.

📅 Part 1: Git Collaboration Q&A (Addressing Concerns)

Q1: The local directory clones all the code — will the files be huge and slow down local builds?

  • No.
  • The [.gitignore] in the repository already filters out bulky third-party dependency packages (such as node_modules) and temporary cache directories produced by builds (such as Android/iOS build artifacts).
  • The local Git directory is very small and lightweight. When debugging locally, the simulator reads these source files and hot-compiles them locally, without consuming extra cloud or Git storage.

Q2: A teammate updated the code in the cloud — how do I make sure pulling updates locally does not overwrite the code I am working on?

  • Git has a safe conflict-blocking mechanism. If you have unsaved local changes and there is a risk of conflict when running git pull directly, Git will refuse the merge and issue a warning; it will never silently overwrite your work.
  • Best practice for safe syncing (the Stash method):
    1. Run git stash to temporarily place your current changes into a "safe box";
    2. Run git pull --rebase to fetch the latest changes from the cloud;
    3. Run git stash pop to restore your changes on top of the latest code.

Q3: What should I do if a code conflict (Conflict) occurs?

  • When you and a teammate have modified the same line of the same file, running git stash pop or merging will report a Conflict.
  • The conflicted file will then have special marker lines inserted (such as <<<<<<< and >>>>>>>), marking your code and your teammate's code respectively.
  • How to handle it:
    1. Carefully compare both sides' code logic, manually choose which side to keep, or combine the two.
    2. After confirming the result is correct, delete the marker lines and save the file again.
    3. In the chat, you can also send the conflicting code or the output of git diff directly to the AI assistant; the AI will automatically analyze the cause for you and provide the safest, most sensible merge plan.

Q4: What are the main branch and other branches for? How are they used when reporting results?

  • The main branch represents the most stable, runnable online version; untested code must never be developed directly on it.
  • feature branches are independent development sandboxes. Each developer should create a new branch when developing a feature (e.g. feature/3.1-qr-gen).
  • Advantage for milestone reporting:
    When reporting Phase 2 results, even if others are developing Phase 3 with unfinished code, you only need to run git checkout feature/phase2-outcome locally to switch to the Phase 2 branch, and the simulator will run only that phase's clean code, ensuring a flawless demo.

📝 Part 2: Team Code Management Guidelines (Initial)

To standardize team development, all team members should strictly follow the collaboration workflow below:

1. Branch naming conventions

All new features or bug fixes must branch off from the latest main branch; pushing directly to main is prohibited.
* New feature branches: feature/<task-number>-<short-feature-name> (e.g. feature/2.1-preview)
* Bug fix branches: fix/<task-number>-<short-defect-name> (e.g. fix/1.3-stale-closure)

2. Daily sync and development workflow

Developers are advised to run the following standard procedure at the start and end of each coding day:

# 1. Switch back to the main branch and get the latest updates
git checkout main
git pull

# 2. Create or switch to your own feature branch
git checkout -b feature/your-feature-name  # new feature
# or
git checkout feature/your-feature-name     # continue an existing feature

# 3. Merge the latest updates from the main branch (to prevent excessive divergence)
git merge main

3. Commit and push

  • Commit message format:
  • New feature: feat: brief description of the new feature (refs #task-id)
  • Bug fix: fix: brief description of the fixed problem (refs #task-id)
  • Documentation update: docs: which documents were changed
  • Push to the cloud:
    bash git push origin feature/your-feature-name

4. Code review and merging (Pull Request)

  • Once a feature is complete and has passed test evaluation on the local simulator, open a Pull Request (PR) on GitHub targeting main.
  • At least 1 other team member must review the code and confirm testing before it can be merged (Merge) into the main branch.

It is hoped that all team members will jointly follow the above guidelines and work together to maintain the code security and stability of the HKEdgeApp project!

📅 第一部分：Git 协作 Q&A (疑虑解答)

Q1：本地目录克隆了所有代码，文件会不会很大，影响本地编译？

  • 不会。
  • 仓库中的 [.gitignore] 已经过滤掉了庞大的第三方依赖包（如 node_modules）和编译产生的临时缓存目录（如 Android/iOS 构建产物）。
  • 本地 Git 目录非常小且轻量。本地调试时，模拟器会读取这些源文件并在本地进行热编译，不占用额外的云端或 Git 空间。

Q2：同事更新了云端代码，我怎么保证本地更新时不覆盖我正在写的代码？

  • Git 拥有安全的冲突阻断机制。如果您本地有未保存的修改，直接执行 git pull 时如果存在冲突风险，Git 会拒绝合并并发出警告，绝对不会静默覆盖您的工作。
  • 安全同步的最佳实践（Stash 暂存法）：
    1. 运行 git stash 将您当前修改临时存入“保险箱”；
    2. 运行 git pull --rebase 拉取云端最新的修改；
    3. 运行 git stash pop 把您的修改恢复到最新代码之上。

Q3：如果发生了代码冲突（Conflict）该怎么做？

  • 当您与同事修改了同一个文件的同一行代码时，在执行 git stash pop 或合并时会提示 Conflict。
  • 此时冲突文件会被插入特殊的标记线（如 <<<<<<< 和 >>>>>>>），分别标记您和同事的代码。
  • 处理方案：
    1. 仔细对比双方代码逻辑，手动选择保留哪一方，或将两者逻辑结合。
    2. 确认无误后删除标记线，重新保存文件。
    3. 在对话中，您也可以直接向 AI 助手发送冲突代码或运行 git diff，AI 会自动为您分析成因并提供最安全、最合理的合并方案。

Q4：Main 分支和 Branch 有什么用？在成果汇报时怎么用？

  • main 分支代表线上最稳定的可运行版本，绝不允许直接在上面开发未测试的代码。
  • feature 分支则是独立的开发沙盒。每个开发者开发一个功能时，需要新建一个分支（如 feature/3.1-qr-gen）。
  • 阶段性汇报优势：
    在汇报 Phase 2 成果时，即使其他人在开发 Phase 3 且代码尚未写完，您也只需在本地运行 git checkout feature/phase2-outcome 切换到 Phase 2 专有分支，模拟器将只运行该阶段的干净代码，确保演示完美无瑕。

📝 第二部分：团队代码管理规范 (初步)

为规范团队开发，所有团队成员应严格遵守以下协作流程：

1. 分支命名规范

所有新功能或 Bug 修复，必须从最新的 main 分支拉出独立分支，禁止直接推送到 main 分支。
* 新功能分支：feature/任务序号-功能简写（例如 feature/2.1-preview）
* Bug 修复分支：fix/任务序号-缺陷简写（例如 fix/1.3-stale-closure）

2. 每日同步与开发流程

建议开发者每天开始写代码前和结束时，执行以下标准流程：

# 1. 切换回主分支并获取最新更新
git checkout main
git pull

# 2. 创建或切换到自己的功能分支
git checkout -b feature/your-feature-name  # 新功能
# 或者
git checkout feature/your-feature-name     # 续写旧功能

# 3. 合并主分支的最新更新（防止分叉过大）
git merge main

3. 代码提交（Commit）与推送（Push）

  • 提交信息格式：
  • 新增功能：feat: 简要描述新增功能 (关联 #任务ID)
  • 修复缺陷：fix: 简要描述修复的问题 (关联 #任务ID)
  • 文档更新：docs: 修改了哪些文档
  • 推送至云端：
    bash git push origin feature/your-feature-name

4. 代码评审与合并（Pull Request）

  • 当功能开发完毕并在本地模拟器通过测试评估后，在 GitHub 上发起指向 main 的 Pull Request (PR)。
  • 团队中至少需要 1 位其他成员 审查代码并确认测试无误后，方可合并（Merge）至 main 主分支。

希望团队成员能共同遵守以上规范，共同维护 HKEdgeApp 项目的代码安全与稳定性！
