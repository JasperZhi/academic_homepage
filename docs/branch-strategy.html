1. Branch Architecture · 分支架构

main ────────────────────────────────────────  生产环境（只合并，不直接改）
  │
  ├── develop ───────────────────────────────  开发主线（所有 feature 汇总）
  │     │
  │     ├── feature/<name> ──────────────────  共享代码功能开发
  │     ├── fix/<name> ──────────────────────  共享代码 Bug 修复
  │     │
  │     ├── ios/<name> ──────────────────────  iOS 原生层改动
  │     └── android/<name> ──────────────────  Android 原生层改动
  │
  └── release/x.x.x ─────────────────────────  发布分支（临时，发布后删除）

2. ⚠️ Key Concept: Only 2 Permanent Branches · 核心概念：只有2条永久分支

这是整个策略最重要的点，先理解清楚：

GitHub 上永远只保留：          feature/ ios/ android/ 是临时工：

main     ← 1 条（永久）        有人开始干活 → 临时创建
develop  ← 1 条（永久）        写完合进 develop → 立刻删除
分支 生命周期 何时出现 何时消失
main 永久 项目创建时 永不删除
develop 永久 项目创建时 永不删除
feature/* 临时 开发新功能时 git checkout -b feature/xxx 合进 develop 后删除
ios/* 临时 改 iOS 原生层时 git checkout -b ios/xxx 合进 develop 后删除
android/* 临时 改 Android 原生层时 git checkout -b android/xxx 合进 develop 后删除
release/* 临时 准备发布时 发布后删除

不要把「分支」和「目录」搞混

分支负责隔离不同人的工作——让你和张三同时改代码不冲突。

目录负责物理分层——代码本身就是按平台分好的：

HKEdgeApp/                  ← 一个仓库，一套分支策略
├── ios/          🍎        ← 只放 iOS 原生文件，物理隔离
├── android/      🤖        ← 只放 Android 原生文件，物理隔离
├── api/          🔷        ← 共享代码，跨平台
├── components/   🔷
├── screen/       🔷
├── context/      🔷
└── constants/    🔷

分支前缀 ios/ android/ 的作用是告诉团队这个分支改的是哪个目录，跟目录结构保持一致，方便一眼看出改动范围。

3. Branch Types · 四种分支

2.1 共享代码分支 feature/* fix/*

改什么：api/ components/ screen/ context/ constants/ assets/ docs/

这些都是跨平台的 JavaScript/TypeScript 代码，不涉及任何原生层。

# 开始新功能
git checkout develop
git checkout -b feature/qr-offline-support

# 开发 → 提交 → 推送
git add -A
git commit -m "feat: offline QR code support"
git push origin feature/qr-offline-support

# 在 GitHub 上创建 PR → target: develop

命名规范：
- feature/qr-offline — 离线 QR 码
- feature/claim-pagination — 理赔列表分页
- fix/stale-closure-bug — 闭包 Bug 修复
- fix/platform-font-crash — 字体崩溃修复

2.2 iOS 原生分支 ios/*

改什么：只改 ios/ 目录下的文件

文件 常见改动
Info.plist 权限声明（相机、推送、位置）
Podfile 添加/删除原生依赖
AppDelegate.swift 生命周期、推送注册
project.pbxproj 构建配置、签名
LaunchScreen.storyboard 启动画面
*.entitlements Capabilities 配置 
git checkout develop
git checkout -b ios/add-camera-permission

# 只动 ios/Info.plist
git add ios/
git commit -m "ios: add camera permission for QR scanning"
git push origin ios/add-camera-permission

2.3 Android 原生分支 android/*

改什么：只改 android/ 目录下的文件

文件 常见改动
AndroidManifest.xml 权限声明、Activity 配置
app/build.gradle 依赖、版本号、签名配置
MainActivity.kt 生命周期、Intent 处理
build.gradle 全局构建配置
proguard-rules.pro 混淆规则
mipmap-* App 图标 
git checkout develop
git checkout -b android/fix-keystore

# 只动 android/app/build.gradle
git add android/
git commit -m "android: fix release keystore config"
git push origin android/fix-keystore

2.4 发布分支 release/*

# 从 develop 拉发布分支
git checkout develop
git checkout -b release/1.0.0

# 修最后一轮 bug → 合并到 main + develop
git checkout main && git merge release/1.0.0
git checkout develop && git merge release/1.0.0

# 打 tag
git tag -a v1.0.0 -m "First release"
git push origin main develop v1.0.0

# 删除发布分支
git branch -d release/1.0.0
git push origin --delete release/1.0.0

5. Workflow · 日常协作流程

场景 A：开发一个新功能（改共享代码）

# 1. 从 develop 拉分支
git checkout develop
git pull origin develop
git checkout -b feature/offline-qr

# 2. 开发，只改 api/ screen/ components/ 等
# ...

# 3. 提交
git add api/cache.js screen/QRCodeScreen.tsx
git commit -m "feat: cache QR token for offline display"
git push origin feature/offline-qr

# 4. 去 GitHub 创建 PR
#    base: develop  ← compare: feature/offline-qr

# 5. Code review → merge → delete branch

场景 B：改 iOS 原生配置

git checkout develop
git checkout -b ios/push-notification
# 改 ios/Info.plist、ios/HKEdgeApp/AppDelegate.swift
git add ios/
git commit -m "ios: add push notification capability"
git push origin ios/push-notification
# PR: base: develop ← compare: ios/push-notification

场景 C：同时改平台 + 共享代码

# 拉一个 feature 分支，同时包含平台改动
git checkout -b feature/qr-with-camera

# 改 shared code
vim screen/QrScanScreen.js
vim api/qrApi.js

# 改 iOS
vim ios/HKEdgeApp/Info.plist

# 改 Android
vim android/app/src/main/AndroidManifest.xml

# 提交时分别说明
git add screen/ api/ && git commit -m "feat: add camera QR scanning UI + API"
git add ios/          && git commit -m "ios: add camera permission for QR scan"
git add android/      && git commit -m "android: add camera permission for QR scan"

10. How to Avoid Merge Conflicts · 如何避免合并冲突

Git 按「行」追踪，不是按「文件」

两个人改不同的文件          → 永不冲突 ✅
两个人改同一个文件的不同行    → Git 自动合并 ✅
两个人改同一个文件的同一行    → 人造冲突 ⚠️

实际场景演示

场景：张三改前端 QR，李四改后端加 JWT

起点：
develop ──●

张三：                         李四：
git checkout -b                git checkout -b
feature/qr-offline             feature/backend-jwt
      │                              │
      ▼                              ▼
  改 screen/QRCodeScreen.tsx      改 ../hkedge-server/server.js
  改 api/cache.js                 改 api/auth middleware
      │                              │
      ▼                              ▼
  git push                       git push

张三改的文件：                   李四改的文件：
├── screen/QRCodeScreen.tsx     ├── ../hkedge-server/server.js
└── api/cache.js                └── ../hkedge-server/middleware/auth.js

               没有任何文件交集 ✅


李四先合：
develop ──●────────────●
                       │ ← backend-jwt 合入

张三后合：
develop ──●────────────●──────────●
                                    │ ← qr-offline 合入
                                    │
                    因为改的文件完全不同，Git 自动合并，零冲突 ✅

什么情况下会冲突？

张三改 QRCodeScreen.tsx 第 50 行：
  const [token, setToken] = useState(null)

李四也改 QRCodeScreen.tsx 第 50 行：
  const [token, setToken] = useState('')
                                    ↑
                              同一行，不同值

Git 会在文件中标记：

<<<<<<< HEAD           ← 李四先合进去的版本
const [token, setToken] = useState('')
=======
const [token, setToken] = useState(null)   ← 张三的版本
>>>>>>> feature/qr-offline

张三手动选择保留哪个，保存，git add → git commit，冲突解决。

三招防冲突

1. 分支要小、要短命

❌ feature/all-backend        ← 改 30 个文件，活 3 周
✅ feature/add-jwt-auth       ← 改 3 个文件，2 天合掉
✅ feature/fix-pagination      ← 改 1 个文件，半天合掉

2. 合之前先把 develop 拉进自己的分支

# 不要在 develop 上直接 merge 自己的分支
# 而是先把自己的分支接到最新的 develop 上

git checkout develop && git pull          # 拉最新的 develop
git checkout my-branch                    # 切回自己的分支
git merge develop                         # 把 develop 融进来

# → 如果有冲突，现在在自己的分支上解决
# → 解决完 push 上去，PR 就是干净的，审查者不会看到冲突

3. 前后端天然隔离

本项目的前端和后端不在同一个文件夹：

前端人 → 只改 HKEdgeApp/api/ screen/ components/ context/
后端人 → 只改 hkedge-server/server.js hkedge-server/public/
        → 几乎不可能撞到同一行代码

冲突了怎么办？

1. 不要慌，冲突是正常的，它只是 Git 在问你"用哪个版本？"
2. 打开冲突文件，找到 <<<<<<< ======= >>>>>>> 标记
3. 决定保留哪个版本（或合并两个版本）
4. 删除标记，保存文件
5. git add <文件> → git commit → git push
6. PR 自动变为绿色

如果搞不定，找写另一边的同事一起看，一人选一半就行。
