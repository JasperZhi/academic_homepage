1. Branch Architecture

main ────────────────────────────────────────  Production (merge-only, no direct edits)
  │
  ├── develop ───────────────────────────────  Main development line (all features merge here)
  │     │
  │     ├── feature/<name> ──────────────────  Shared-code feature development
  │     ├── fix/<name> ──────────────────────  Shared-code bug fixes
  │     │
  │     ├── ios/<name> ──────────────────────  iOS native-layer changes
  │     └── android/<name> ──────────────────  Android native-layer changes
  │
  └── release/x.x.x ─────────────────────────  Release branch (temporary, deleted after release)

2. ⚠️ Key Concept: Only 2 Permanent Branches

This is the single most important point of the whole strategy; understand it first:

GitHub keeps forever:          feature/ ios/ android/ are temporary:

main     ← 1 (permanent)       someone starts work → create temporarily
develop  ← 1 (permanent)       work merged into develop → delete immediately
Branch Lifetime When it appears When it disappears
main Permanent At project creation Never deleted
develop Permanent At project creation Never deleted
feature/* Temporary When developing a new feature: git checkout -b feature/xxx Deleted after merging into develop
ios/* Temporary When changing the iOS native layer: git checkout -b ios/xxx Deleted after merging into develop
android/* Temporary When changing the Android native layer: git checkout -b android/xxx Deleted after merging into develop
release/* Temporary When preparing a release Deleted after release

Do not confuse "branches" with "directories"

Branches isolate different people's work — so that you and a teammate can edit code at the same time without conflict.

Directories provide the physical layering — the code itself is already split by platform:

HKEdgeApp/                  ← one repository, one branch strategy
├── ios/          🍎        ← iOS native files only, physically isolated
├── android/      🤖        ← Android native files only, physically isolated
├── api/          🔷        ← shared code, cross-platform
├── components/   🔷
├── screen/       🔷
├── context/      🔷
└── constants/    🔷

The branch prefixes ios/ and android/ tell the team which directory the branch modifies. They mirror the directory structure so the scope of a change is visible at a glance.

3. Branch Types

2.1 Shared-code branches feature/* fix/*

What they modify: api/ components/ screen/ context/ constants/ assets/ docs/

All of these are cross-platform JavaScript/TypeScript code, with no native-layer involvement.

# Start a new feature
git checkout develop
git checkout -b feature/qr-offline-support

# Develop → commit → push
git add -A
git commit -m "feat: offline QR code support"
git push origin feature/qr-offline-support

# Create a PR on GitHub → target: develop

Naming conventions:
- feature/qr-offline — offline QR code
- feature/claim-pagination — claim list pagination
- fix/stale-closure-bug — stale closure bug fix
- fix/platform-font-crash — font crash fix

2.2 iOS native branches ios/*

What they modify: files under the ios/ directory only

File Typical changes
Info.plist Permission declarations (camera, push, location)
Podfile Adding/removing native dependencies
AppDelegate.swift Lifecycle, push registration
project.pbxproj Build configuration, signing
LaunchScreen.storyboard Launch screen
*.entitlements Capabilities configuration 
git checkout develop
git checkout -b ios/add-camera-permission

# Only ios/Info.plist is touched
git add ios/
git commit -m "ios: add camera permission for QR scanning"
git push origin ios/add-camera-permission

2.3 Android native branches android/*

What they modify: files under the android/ directory only

File Typical changes
AndroidManifest.xml Permission declarations, Activity configuration
app/build.gradle Dependencies, version code, signing configuration
MainActivity.kt Lifecycle, Intent handling
build.gradle Global build configuration
proguard-rules.pro Obfuscation rules
mipmap-* App icons 
git checkout develop
git checkout -b android/fix-keystore

# Only android/app/build.gradle is touched
git add android/
git commit -m "android: fix release keystore config"
git push origin android/fix-keystore

2.4 Release branches release/*

# Cut a release branch from develop
git checkout develop
git checkout -b release/1.0.0

# Fix the last round of bugs → merge into main + develop
git checkout main && git merge release/1.0.0
git checkout develop && git merge release/1.0.0

# Tag it
git tag -a v1.0.0 -m "First release"
git push origin main develop v1.0.0

# Delete the release branch
git branch -d release/1.0.0
git push origin --delete release/1.0.0

10. How to Avoid Merge Conflicts

Git tracks "lines", not "files"

Two people change different files          → never conflicts ✅
Two people change different lines of the same file → Git merges automatically ✅
Two people change the same line of the same file → human-made conflict ⚠️

Worked example

Scenario: Person A changes the frontend QR, Person B adds JWT on the backend

Starting point:
develop ──●

Person A:                        Person B:
git checkout -b                  git checkout -b
feature/qr-offline               feature/backend-jwt
      │                                │
      ▼                                ▼
  edits screen/QRCodeScreen.tsx    edits ../hkedge-server/server.js
  edits api/cache.js               edits api/auth middleware
      │                                │
      ▼                                ▼
  git push                         git push

Files Person A changed:          Files Person B changed:
├── screen/QRCodeScreen.tsx      ├── ../hkedge-server/server.js
└── api/cache.js                 └── ../hkedge-server/middleware/auth.js

               No overlapping files at all ✅


Person B merges first:
develop ──●────────────●
                       │ ← backend-jwt merged in

Person A merges second:
develop ──●────────────●──────────●
                                    │ ← qr-offline merged in
                                    │
                    Because the changed files are completely different,
                    Git merges automatically with zero conflicts ✅

When does a conflict occur?

Person A changes line 50 of QRCodeScreen.tsx:
  const [token, setToken] = useState(null)

Person B also changes line 50 of QRCodeScreen.tsx:
  const [token, setToken] = useState('')
                                    ↑
                              same line, different values

Git marks it in the file:

<<<<<<< HEAD           ← the version Person B merged in first
const [token, setToken] = useState('')
=======
const [token, setToken] = useState(null)   ← Person A's version
>>>>>>> feature/qr-offline

Person A manually chooses which version to keep, saves, runs git add → git commit, and the conflict is resolved.

Three habits that prevent conflicts

1. Keep branches small and short-lived

❌ feature/all-backend        ← touches 30 files, lives 3 weeks
✅ feature/add-jwt-auth       ← touches 3 files, merged in 2 days
✅ feature/fix-pagination      ← touches 1 file, merged in half a day

2. Before merging, pull develop into your own branch

# Do not merge your branch into develop directly
# Instead, first bring your branch up to the latest develop

git checkout develop && git pull          # get the latest develop
git checkout my-branch                    # switch back to your branch
git merge develop                         # merge develop into it

# → If there are conflicts, resolve them now on your own branch
# → Push after resolving; the PR will be clean and reviewers will see no conflicts

3. Frontend and backend are naturally isolated

The frontend and backend of this project are not in the same folder:

Frontend person → touches only HKEdgeApp/api/ screen/ components/ context/
Backend person → touches only hkedge-server/server.js hkedge-server/public/
        → practically impossible to hit the same line of code

What to do when a conflict happens

1. Don't panic; conflicts are normal. Git is just asking "which version do you want?"
2. Open the conflicted file and find the <<<<<<< ======= >>>>>>> markers
3. Decide which version to keep (or combine both)
4. Delete the markers and save the file
5. git add <file> → git commit → git push
6. The PR turns green automatically

If you can't resolve it, sit down with the teammate who wrote the other side
and pick one side each.

不要把「分支」和「目录」搞混

分支负责隔离不同人的工作——让你和张三同时改代码不冲突。

目录负责物理分层——代码本身就是按平台分好的：

HKEdgeApp/                  ← 一个仓库，一套分支策略
├── ios/          🍎        ← 只放 iOS 原生文件，物理隔离
├── android/      🤖        ← 只放 Android 原生文件，物理隔离
├── api/          🔷        ← 共享代码，跨平台
├── components/   🔷
├── screen/       🔷
├── context/      🔷
└── constants/    🔷

分支前缀 ios/ android/ 的作用是告诉团队这个分支改的是哪个目录，跟目录结构保持一致，方便一眼看出改动范围。

10. How to Avoid Merge Conflicts · 如何避免合并冲突

Git 按「行」追踪，不是按「文件」

两个人改不同的文件          → 永不冲突 ✅
两个人改同一个文件的不同行    → Git 自动合并 ✅
两个人改同一个文件的同一行    → 人造冲突 ⚠️

实际场景演示

场景：张三改前端 QR，李四改后端加 JWT

起点：
develop ──●

张三：                         李四：
git checkout -b                git checkout -b
feature/qr-offline             feature/backend-jwt
      │                              │
      ▼                              ▼
  改 screen/QRCodeScreen.tsx      改 ../hkedge-server/server.js
  改 api/cache.js                 改 api/auth middleware
      │                              │
      ▼                              ▼
  git push                       git push

张三改的文件：                   李四改的文件：
├── screen/QRCodeScreen.tsx     ├── ../hkedge-server/server.js
└── api/cache.js                └── ../hkedge-server/middleware/auth.js

               没有任何文件交集 ✅


李四先合：
develop ──●────────────●
                       │ ← backend-jwt 合入

张三后合：
develop ──●────────────●──────────●
                                    │ ← qr-offline 合入
                                    │
                    因为改的文件完全不同，Git 自动合并，零冲突 ✅

什么情况下会冲突？

张三改 QRCodeScreen.tsx 第 50 行：
  const [token, setToken] = useState(null)

李四也改 QRCodeScreen.tsx 第 50 行：
  const [token, setToken] = useState('')
                                    ↑
                              同一行，不同值

Git 会在文件中标记：

<<<<<<< HEAD           ← 李四先合进去的版本
const [token, setToken] = useState('')
=======
const [token, setToken] = useState(null)   ← 张三的版本
>>>>>>> feature/qr-offline

张三手动选择保留哪个，保存，git add → git commit，冲突解决。

三招防冲突

1. 分支要小、要短命

❌ feature/all-backend        ← 改 30 个文件，活 3 周
✅ feature/add-jwt-auth       ← 改 3 个文件，2 天合掉
✅ feature/fix-pagination      ← 改 1 个文件，半天合掉

2. 合之前先把 develop 拉进自己的分支

# 不要在 develop 上直接 merge 自己的分支
# 而是先把自己的分支接到最新的 develop 上

git checkout develop && git pull          # 拉最新的 develop
git checkout my-branch                    # 切回自己的分支
git merge develop                         # 把 develop 融进来

# → 如果有冲突，现在在自己的分支上解决
# → 解决完 push 上去，PR 就是干净的，审查者不会看到冲突

3. 前后端天然隔离

本项目的前端和后端不在同一个文件夹：

前端人 → 只改 HKEdgeApp/api/ screen/ components/ context/
后端人 → 只改 hkedge-server/server.js hkedge-server/public/
        → 几乎不可能撞到同一行代码

冲突了怎么办？

1. 不要慌，冲突是正常的，它只是 Git 在问你"用哪个版本？"
2. 打开冲突文件，找到 <<<<<<< ======= >>>>>>> 标记
3. 决定保留哪个版本（或合并两个版本）
4. 删除标记，保存文件
5. git add <文件> → git commit → git push
6. PR 自动变为绿色

如果搞不定，找写另一边的同事一起看，一人选一半就行。
